## Overview

This update refines the LLM prompt design across four core analysis modules based on a systematic review of peer-reviewed papers and conference proceedings on AI-assisted medical device regulatory compliance. The improvements are grounded in ISO 13485:2016 audit practice, MDSAP multi-country assessment methodology, and recent findings on LLM reliability in regulated environments.

---

## 一、Academic Research Basis

The following papers informed this update:

| Paper | Source | Key Finding Applied |
|-------|--------|---------------------|
| *Standard Applicability Judgment: A RAG-based Framework for Medical Device Compliance* (Han et al.) | arXiv:2506.18511 | Ground all analysis strictly in retrieved regulatory text; confidence < 0.4 when text is insufficient |
| *AI for Regulatory Affairs: Balancing Accuracy, Interpretability and Computational Cost in Medical Device Classification* | arXiv:2505.18695 | Role-based persona prompting (jurisdiction-specific expert) improves output quality; LLM language plausibility ≠ legal correctness (45% vs CNN 88%) |
| *Regulator-Manufacturer AI Agents Modeling: Mathematical Feedback-Driven Multi-Agent LLM Framework* | arXiv:2411.15356 | Structured role separation and iterative feedback loops improve compliance reasoning |
| *Large Language Model Non-compliance with FDA Guidance for Clinical Decision Support Devices* | PMC11419185 | Prompts alone are insufficient to guarantee compliance; "language plausibility ≠ legal correctness" must be explicit in system instructions |
| *Applying and Validating a QMS for In-house Developed Medical Software* | PMC11996894 | ISO 13485 gap analysis distributes as: sufficient 32% / incomplete 23% / entirely lacking 45% — all three categories must be distinguished |
| *Implementing QMS to Close the AI Translation Gap in Health AI* | PMC10676432 | FDA GMLP as lifecycle baseline; staged regulatory rigor by maturity level |

## 二、Changed Files

### 1. `src/analysis/regulation_analyzer.py`

**Function:** `_build_clause_batch_prompt` and `_build_unique_requirements_prompt`

#### What Changed

| Aspect | Before | After |
|--------|--------|-------|
| LLM Persona | Generic "medical device regulatory expert" | Senior RA specialist with MDSAP multi-country audit experience (Asia-Pacific, EU, North America) |
| Reasoning Structure | Single-step mapping | 4-step chain-of-thought: explicit search → functional equivalence check → completeness assessment → confidence calibration |
| Evidence Grounding | Not specified | Must cite specific article/section; confidence < 0.4 when crawled text is insufficient |
| Plausibility vs Correctness | Not addressed | Explicit rule: "language plausibility ≠ legal correctness; similar terminology ≠ substantive coverage" |
| Confidence Floor | No minimum | `na` + confidence 0.25 when evidence is absent (was 0.3, tightened) |
| Unique Requirements Scope | 8 categories | Expanded to 10 categories, added PSUR and UDI/traceability system requirements |
| Unique Req. Audit Criteria | Generic | Specific "MDSAP auditor physical inspection" framing for expected_evidence |

#### Key Prompt Additions

```
STEP-BY-STEP REASONING for each clause:
  Step 1: Search the regulatory text for explicit mention of the clause topic.
  Step 2: Check if functionally equivalent requirements exist under different terms.
  Step 3: Assess completeness — does it cover all sub-requirements of the clause?
  Step 4: Assign status and calibrate confidence based on text evidence quality.
```

### 2. `src/analysis/gap_scanner.py`

**Constants:** `_SYSTEM_PROMPT` and `_DOC_SYSTEM_PROMPT`

#### What Changed

| Aspect | Before | After |
|--------|--------|-------|
| Role Definition | Generic QMS document search assistant | ISO 13485:2016 audit-support search assistant using Objective Evidence principles |
| Gap Classification | Binary (found / not found) + is_inadequate flag | Explicit 3-category classification: sufficient / incomplete / lacking entirely |
| Sufficiency Criteria | Vague ("insufficient to cover requirement") | Concrete: document must describe "how to execute" including responsible party, frequency, measurable criteria |
| Plausibility Check | Not addressed | Explicit: "similar terminology ≠ substantive regulatory coverage; verify actual procedural content" |
| Outdated Detection | is_outdated field present but criteria unclear | Explicit: flag if document references superseded standards (e.g., ISO 13485:2003 instead of 2016) |

#### Key Prompt Additions

```
區分三種結果（根據 ISO 13485 稽核實務）：
  - 充分: 文件明確描述「如何執行」，包含程序、責任人及可量測標準
  - 不充分: 文件提到此要求但缺乏具體程序、責任人、頻率或可量測標準
  - 缺失: 文件中完全找不到相關內容
```

## 四、Design Principles Applied

These changes embody three principles established by the academic literature:

1. **Persona grounding over generic expertise** — Jurisdiction-specific, audit-credential role definitions produce more legally accurate outputs than generic "expert" labels (arXiv:2505.18695).

2. **Evidence-first, not plausibility-first** — All prompts now explicitly distinguish between language that sounds compliant and language that substantively meets regulatory requirements (PMC11419185).

3. **Structured output with calibrated uncertainty** — Confidence scores are now tied to explicit evidence quality criteria, reducing overconfident outputs when regulatory text is sparse (arXiv:2506.18511).
