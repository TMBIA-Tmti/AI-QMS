### 1. `httpx[http2]` 套件遺漏 — 法規爬蟲啟動失敗

| 項目 | 說明 |
|------|------|
| **問題現象** | 執行「法規清單更新」指令時，`regulatory_crawler.py` 啟動法規爬蟲失敗 |
| **錯誤位置** | `src/services/regulatory_crawler.py` → `_ensure_client()` → `httpx.AsyncClient(http2=True)` |

**實際錯誤訊息：**

```
ImportError: Using http2=True, but the 'h2' package is not installed.
Install using `pip install h2`.
```

**為什麼會發生這個問題：**

這是一個典型的「**開發環境汙染（Development Environment Pollution）**」問題。在 Python 生態中，`httpx` 套件的 HTTP/2 支援是透過 **extras** 機制提供的。`httpx` 本身只包含 HTTP/1.1 功能，要支援 HTTP/2 必須安裝額外的子套件 `h2`、`hpack`、`hyperframe`。

在 `requirements.txt` 中，原本只寫了：
```
httpx>=0.27.0
```
而正確的寫法應該是：
```
httpx[http2]>=0.27.0
```

開發者的本機環境中，`h2` 套件因為之前安裝其他套件（例如 `grpcio`、`hyper` 等）時被順帶安裝，所以開發環境不會觸發此問題。但當專案被部署到一台乾淨的電腦（例如新同事的電腦、新的 Conda 環境），透過 `pip install -r requirements.txt` 安裝時，只會安裝 `httpx` 本體，不會安裝 `h2`，導致啟動法規爬蟲時立刻報 `ImportError`。

**修正方案：**

將 `requirements.txt` 中 `httpx>=0.27.0` 改為 `httpx[http2]>=0.27.0`。pip 的 extras 語法 `[http2]` 會告訴 pip 同時安裝 `h2`、`hpack`、`hyperframe` 等 HTTP/2 支援套件。

**影響範圍：** 所有使用 `pip install -r requirements.txt` 的環境。三個 `.bat` 啟動腳本（`start.bat`、`start_chainlit.bat`、`start_phoenix.bat`）都有自動更新機制 `pip install -r requirements.txt --quiet`，更新後下次啟動自動安裝。

**預防措施：**
- 使用 `pipdeptree` 或 `pip check` 定期比對實際 import 與 `requirements.txt`
- CI/CD 加入「乾淨環境安裝測試」
- extras 標記（`[http2]`、`[security]`）必須明確記錄

### 2. Windows NTFS 權限錯誤 — `PermissionError: [Errno 13]`

| 項目 | 說明 |
|------|------|
| **問題現象** | 在其他電腦部署時，多個資料夾寫入失敗 |
| **受影響目錄** | `data/user_settings/anonymous.json`、`data/model_cache.json`、`.files/`、`uploads/` |

**實際錯誤訊息：**

```
PermissionError: [Errno 13] Permission denied: 'data/user_settings/anonymous.json'
PermissionError: [Errno 13] Permission denied: 'data/model_cache.json'
PermissionError: [Errno 13] Permission denied: '.files/'
```

**為什麼會發生這個問題：**

Windows NTFS 檔案系統的權限管理有**兩套獨立的機制**：

1. **ACL（Access Control List）**：由 Windows 安全性描述項控制，決定哪些使用者/群組可以讀取、寫入、執行特定檔案或資料夾。
2. **唯讀屬性（Read-Only Attribute）**：檔案層級的簡單旗標，獨立於 ACL 運作。

即使 Python 的 `os.makedirs()` 或 `Path.mkdir(parents=True, exist_ok=True)` 成功建立了目錄，以下情況仍會導致寫入失敗：

- **不同 Windows 帳號建立的目錄**：A 帳號建立的資料夾，B 帳號預設沒有寫入權限
- **從 ZIP 解壓縮**：ZIP 解壓時可能繼承壓縮檔的唯讀屬性
- **Git clone**：Git 在 Windows 上 clone 時，某些情況下會設定唯讀屬性
- **`.files/` 目錄**：這是 Chainlit 框架自動建立的上傳暫存目錄，不在應用程式碼控制範圍內

此外，使用者嘗試用 `icacls` 修復權限時，PowerShell 會將 `(OI)(CI)F` 中的括號解析為子表達式，導致指令失敗：

```powershell
# 錯誤寫法（PowerShell 解析括號為子表達式）
icacls data /grant UserName:(OI)(CI)F /T

# 正確寫法（將整段參數包在引號內）
icacls data /grant "UserName:(OI)(CI)F" /T
```

**修正方案：**

在 `app.py` 啟動時加入目錄初始化函式 `ensure_directories()`：

1. 列出所有需寫入的目錄清單（`data/`、`data/user_settings/`、`data/analysis_cache/`、`data/exports/`、`.files/`、`uploads/`、`markdown_storage/`、`regulatory_analysis_storage/`、`regulatory_markdown_storage/`）
2. 逐一 `mkdir` + 寫入測試檔（`.write_test`）+ 刪除測試檔
3. 若權限不足，在啟動時明確提示使用者

同時，`src/utils/safe_io.py` 新增了 `_atomic_write_json` 機制，所有 JSON 寫入操作改用原子寫入 + `PermissionError` 自動重試。

**附帶修正：**

`src/utils/user_settings.py` 中的 `_atomic_write_json` 已實作重試機制（對應 git commit `a2c3805`：`fix(settings): atomic write with retry to prevent PermissionError on Windows`），其他模組（如 `llm_providers.py` 的 `model_cache.json`）也應採用相同模式。

### 3. PDF OCR 失敗 — Poppler 未安裝

| 項目 | 說明 |
|------|------|
| **問題現象** | 上傳 PDF 檔案時，LLM Vision OCR 失敗 |
| **錯誤位置** | `src/ocr/vision_ocr.py` → LLM Vision fallback 路徑 |

**實際錯誤訊息：**

```
Unable to get page count. Is poppler installed and in PATH?
```

**為什麼會發生這個問題：**

系統的 PDF OCR 處理流程設計為二層架構：

```
PDF 上傳
  ↓
[Layer 1] MarkItDown 處理 → 成功提取文字？
  ↓ 是 → 使用 MarkItDown 結果（~1秒/檔，零 Token）
  ↓ 否（掃描型 PDF，提取 0 字元）
[Layer 2] LLM Vision 備援 → 需要 poppler 將 PDF 轉為圖片
  ↓
poppler 未安裝 → 報錯
```

`poppler` 是一個 C++ 編寫的 PDF 渲染引擎，Python 的 `pdf2image` 套件依賴它來將 PDF 頁面轉換為圖片。但 `poppler` 不是 Python 套件（無法通過 pip 安裝），它是一個**作業系統層級的外部依賴**，需要單獨安裝：

- **Windows**：下載 [poppler for Windows](https://github.com/oschwartz10612/poppler-windows/releases/) 並加入 PATH
- **Linux**：`sudo apt-get install poppler-utils`
- **macOS**：`brew install poppler`

**受影響文件類型：** 掃描型 PDF（影像型，MarkItDown 無法提取文字），例如：
- `4-SD-011 銷貨單 V07 簽名檔.pdf`
- `4-MD-059 NimBO保養維修需求與入出貨點檢紀錄單V03.pdf`
- `4-MD-005 廠區圖 V08.pdf`
- `4-MD-020 維修重工工單 V08 簽名頁.pdf`

**修正方案：**
1. 在 README 安裝指南中加入 poppler 安裝說明
2. 在 `start.bat` 中加入 poppler 存在性檢查
3. 若 poppler 不可用，改用純 Python 的 `PyMuPDF (fitz)` 作為第二層 fallback

### 4. LLM Vision OCR 不支援的圖片格式 — `media_type` 錯誤

| 項目 | 說明 |
|------|------|
| **問題現象** | 部分 PDF 經 poppler 轉圖後，送到 Anthropic API 時被拒絕 |

**實際錯誤訊息：**

```
HTTP 400 Bad Request
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "Input should be 'image/jpeg', 'image/png', 'image/gif' or 'image/webp'"
  }
}
```

**為什麼會發生這個問題：**

不同的 LLM 提供商對圖片格式的支援範圍不同。Anthropic Claude 只接受 4 種格式：`image/jpeg`、`image/png`、`image/gif`、`image/webp`。

當 poppler 將 PDF 轉換為圖片時，預設可能產生 TIFF、BMP 等格式（取決於 PDF 內嵌的圖像格式和 poppler 的設定）。程式碼在發送圖片到 LLM API 前，沒有檢查或轉換 `media_type`，直接將不支援的格式發送出去，導致 API 回傳 400 錯誤。

**修正方案：**

在 `vision_ocr.py` 中，發送圖片到 LLM 前增加 media_type 白名單驗證：

```python
SUPPORTED_MEDIA_TYPES = {"image/jpeg", "image/png", "image/gif", "image/webp"}

if media_type not in SUPPORTED_MEDIA_TYPES:
    # 使用 Pillow 將圖片轉換為 PNG
    from PIL import Image
    img = Image.open(image_path)
    png_path = image_path.with_suffix(".png")
    img.save(png_path, "PNG")
    media_type = "image/png"
```

### 5. 簽章偵測誤判 — 大量假陽性（False Positive）

| 項目 | 說明 |
|------|------|
| **問題現象** | 56 份正式文件測試中，多份無簽章文件被標記為「✅ 簽章偵測通過」 |
| **誤判範例** | 客戶滿意度調查表（空白模板）、訓練簽到表、報價單等 |

**為什麼會發生這個問題：**

系統的簽章偵測使用 200+ 個多語言關鍵字（如「核准」「審核」「Approved by」「承認」等）進行文字匹配。偵測邏輯為：**只要文件 OCR 內容中出現任一關鍵字，就判定文件有簽章**。

問題在於，這些關鍵字不只會出現在「已簽署的簽章區域」，也會出現在：

1. **空白表格的欄位標題**：例如「審核」這個字出現在表頭列，但欄位內容是空的
2. **Excel 工作表的列標題**：例如「簽核」欄的標題本身就包含關鍵字
3. **文件內容中的描述性文字**：例如「本文件經核准後生效」這種規範性敘述

結果造成大量「假陽性」— 偵測到了關鍵字，但那只是欄位名稱或敘述文字，並非實際的簽名或印章。

**修正方案：**

新增「簽章檢測模式開關」功能。在 Eira 歡迎流程中（使用者輸入名字後），詢問是否啟用簽章偵測模式：

- **啟用模式**：維持現有 200+ 關鍵字簽章偵測 + 使用者確認流程
- **停用模式**：跳過簽章偵測，所有文件直接通過。進版偵測、文件作廢、版本管理等功能不受影響

選擇結果存入 `cl.user_session`，整個對話期間有效。20 語言全部新增 i18n 鍵值：
- `eira.signature_mode_prompt`
- `eira.signature_mode_enabled`
- `eira.signature_mode_disabled`
- `eira.signature_mode_yes`
- `eira.signature_mode_no`

**未來改善方向：**
- 區分「欄位標題」與「實際填寫的簽章/印章」
- 加入圖片層級的簽章偵測（用 OpenCV 或 LLM Vision 辨識實際簽名圖像）

### 6. 版本偵測誤判 — 不同文件被視為同一文件的進版

| 項目 | 說明 |
|------|------|
| **問題現象** | `2-RD-001 風險管理程序書 V07` 與 `3-RD-001 圖號編碼與申請辦法 V02` 被判定為同一文件的版本更新 |

**為什麼會發生這個問題：**

版本偵測邏輯在比對文件編號時，使用正則表達式提取文件編號。例如從檔名 `2-RD-001 風險管理程序書 V07.pdf` 提取 `RD-001`。問題在於正則表達式**忽略了前綴的階層編號**（`2-` vs `3-`）：

```
2-RD-001 風險管理程序書 V07.pdf  →  提取 doc_id = "RD-001"
3-RD-001 圖號編碼與申請辦法 V02.pdf  →  提取 doc_id = "RD-001"
```

兩份完全不同的文件（不同階層、不同名稱、不同內容），因為 `doc_id` 相同而被系統判定為「同一文件的不同版本」，觸發了進版流程。

**根本原因：** 正則表達式設計時未考慮到 QMS 文件編號的階層前綴是文件唯一識別的一部分。`2-RD-001` 和 `3-RD-001` 是兩份不同的文件，而非同一份文件的不同版本。

**修正方案：**
1. 修正 `detect_document_type()` 中的正則表達式，將完整的文件編號（含階層前綴）作為唯一識別
2. 進版判定前加入「名稱相似度檢查」（Jaccard 或 Levenshtein 距離），若名稱差異過大則不視為進版
3. LLM 差異分析結果若確認「這不是同一份文件」，應阻止進版操作

### 7. 版本號偵測為 `None` — 進版時顯示 `V? → VNone`

| 項目 | 說明 |
|------|------|
| **問題現象** | 部分文件版本號顯示為 `V? → VNone` 或 `V1.0 → VNone` |

**為什麼會發生這個問題：**

版本號解析使用正則表達式從 OCR 提取的文字中匹配版本號。當以下情況發生時，解析結果為 `None`：

1. **非標準格式**：文件使用「版次 02」而非「V02」，正則不匹配
2. **OCR 截斷**：掃描型 PDF 經 MarkItDown OCR 後，版本號所在區域被截斷或辨識錯誤（例如 `V07` 被辨識為 `VO7`、`V0T` 等）
3. **版本號位置特殊**：版本號出現在頁尾、浮水印、或表格的合併儲存格中，OCR 可能無法正確擷取

Python 中，正則表達式 `re.search()` 找不到匹配時回傳 `None`，而程式碼直接將 `None` 嵌入字串模板，產生 `VNone`。

**修正方案：**
- 擴展版本號解析正則表達式，支援更多格式：`V01`、`V1.0`、`版次 02`、`Rev. 2`、`Edition 3`、`第 2 版`
- 解析失敗時顯示 `V?`（而非 `VNone`），並提示使用者手動輸入版本號

### 8. Chainlit `zh-TW` 翻譯檔缺失 — 歡迎頁 Warning

| 項目 | 說明 |
|------|------|
| **問題現象** | 啟動時 log 持續出現警告 |

**實際 Log 訊息：**

```
WARNING: Translated markdown file for zh-TW not found. Defaulting to chainlit.md.
```

**為什麼會發生這個問題：**

Chainlit 框架內建多語言支援機制。當使用者的瀏覽器語言設定為 `zh-TW`（繁體中文）時，Chainlit 會自動尋找 `chainlit_zh-TW.md` 作為歡迎頁面內容。尋找順序為：

```
chainlit_{locale}.md  →  chainlit.md（預設）
```

專案中只有 `chainlit.md`（內容已是中文），但沒有建立 `chainlit_zh-TW.md`。由於找不到 locale-specific 的 markdown 檔案，Chainlit 在每次請求時都會在 server log 中印出 WARNING。

雖然功能上不影響使用（會自動 fallback 到 `chainlit.md`），但：
1. 每次頁面載入都會產生 WARNING log，汙染 log 輸出
2. 若有日後需要針對不同語言顯示不同歡迎頁面，就需要 locale-specific 檔案

**修正方案：**
1. 建立 `chainlit_zh-TW.md`（內容與 `chainlit.md` 相同，因為原版已是中文）
2. 同時建立 `public/logo_light.svg` 和 `public/logo_dark.svg` 品牌 logo，解決另一個 `Missing custom logo` warning

## 二、新增功能（Features）

### 1. 簽章檢測模式開關

- **位置**：文件管制子 Agent 歡迎流程（名字輸入後、Eira 介紹後）
- **功能**：使用者可選擇是否啟用簽章偵測模式
- **啟用模式**：維持現有 200+ 關鍵字簽章偵測 + 使用者確認流程
- **停用模式**：跳過簽章偵測，所有文件直接通過。進版偵測、文件作廢等功能不受影響
- **Session 持久化**：選擇結果存入 `cl.user_session`，整個對話期間有效
- **i18n**：20 語言全部支援

### 2. 法規評估模式選擇（快速 vs 詳細）

使用者可選擇法規評估的深度：

- **⚡ 快速評估報告**：
  - One-shot LLM 模式，所有資料一次性送入
  - 報告區分「有實際資料的分析」與「LLM 專業判斷」
  - 適合快速了解合規狀態
- **📋 詳細評估報告**：
  - 多階段 Pipeline 分析（Phase 0→6）
  - 包含 Gap Scan、Checklist Verify、Risk Assessment、Remediation、Cross-Examination
  - 適合正式稽核準備

### 3. 文件階層分類系統（Document Hierarchy）

- **5 個預設階層**：L1（品質手冊）、L2（程序書）、L3（作業指導書）、L4（表單紀錄）、REG（法規文件）
- **AI 自動分類**：`classify_hierarchy_with_llm()` 上傳後 LLM 自動判定
- **使用者確認/修改 UI**：確認、修改、新增自訂階層按鈕
- **Legacy 相容**：SOP/WI/FORM/DHF/OTHER 自動映射到新階層
- **自訂階層 CRUD**：支援新增自訂階層名稱，JSON 持久化
- **i18n**：20 語言各 12 個 `hierarchy.*` 鍵值

### 4. 文件作廢偵測流程改善

- 上傳流程整合：文件上傳 → 簽章選擇 → 確認上傳 → 偵測「作廢」字眼或作廢章
- 使用者選項：全部不上傳 / 部分上傳（個別文件選擇按鈕）
- 完整稽核追蹤：作廢操作記錄在 SHA-256 雜湊鏈中

### 5. 對話語氣與人稱改善（全 20 語言）

- AI 需要使用者回答時：移除 `Eira：` 前綴，改用 `{name}，{內容}` 格式
- AI 單純回覆/通知時：保持 `Eira：{內容}` 格式
- 涵蓋範圍：20 個 locale JSON + app.py system prompt + HTML 報告頁面 + chainlit markdown 歡迎頁

### 7. 7 國 MDSAP 法規合規系統

基於 git commit `8682382`，新增完整的 MDSAP（Medical Device Single Audit Program）法規合規系統：

- **7 國法規交叉引用**：MDSAP 5 國（美國、加拿大、巴西、日本、澳洲）+ 台灣 TFDA + 歐盟 EU MDR
- **Cross-Examination QA Agent**：Phase 5 MDSAP 驗證，自動交叉詰問法規合規性
- **Daily Audit 系統**：10 天滾動 meta review，自動評分

## 十三、Phase 5 法規辯證管線修復（2026-04-06）

> **commit**: `d02ca92` fix(phase-5): SSE thread-safety, crawled regulation reload, report config wiring  
> **commit**: `6d1a942` fix(phase-5+pipeline): human injection consumption, clause matching expansion

### 13.1 Phase 5 SSE 執行緒安全修復

**問題**：Phase 5 在 `ThreadPoolExecutor` 工作執行緒中直接呼叫 `asyncio.Queue.put_nowait()`，跨執行緒非安全，SSE 事件在瀏覽器端從未顯示。

**修正**：`emit_cross_exam_event` 改用 `loop.call_soon_threadsafe()`：
- 首次 SSE 連線時捕獲事件迴圈（`_sse_loop`）
- 工作執行緒呼叫時透過 `call_soon_threadsafe` 安全派發
- 在事件迴圈內呼叫時直接 `put_nowait`（相容）

### 13.2 Crawled Regulation 重載修復

**問題**：執行「法規清單更新」後，新爬取的法規 profile 已存入磁碟，但未重新載入至 `PREDEFINED_REGULATIONS`，導致 Phase 5 交叉審查時 `selected_regulations` 為空。

**修正**：在 `handle_regulatory_list` 和 `handle_regulatory_update_rescan` 兩個進入點，`get_profile_ids_for_regions()` 呼叫前先執行 `load_all_crawled_regulations()`。

### 13.3 Report Type Fallback 修正

**問題**：`_ask_report_type()` 對話逾時或例外時，硬編碼 fallback 為 `"normal"`（跳過 Phase 4/5/6），導致所有未明確回應的執行都略過 Phase 5。

**修正**：fallback 改為讀取 `get_custom_skip_phases()`（持久化的 HTML 報表面板設定），預設只跳過 `phase_6`，保留 Phase 5。同時明確處理 `"report_type_normal"` 分支，`else` 子句僅在真正逾時時觸發。

### 13.4 Human RA 注入消費（Bug #8）

**問題**：Human RA 介入訊息已儲存並透過 SSE 廣播，但 `verifier.py` 的辯證迴圈從未消費這些訊息，注入對辯證結果無任何影響。

**修正**：`run_verification_row()` 在 Round 1 前及每輪前呼叫 `get_injected_messages(run_id)` 排空佇列。注入的訊息以「Human RA Intervention」區塊附加至 Analyzer 和 Verifier 的提示。消費後廣播 `human_injection_applied` SSE 事件確認。

### 13.5 條款匹配擴展 — 國家法規關鍵字（Bug #9）

**問題**：`_match_doc_to_clauses()` 僅靠 ISO 13485 條款號明文引用匹配（如「ISO 13485 Clause 7.5.3」）。符合 FDA QMSR、EU MDR、TFDA 等國家法規但未明文引用 ISO 條款號的程序文件，在 Phase 5 中被靜默跳過。

**修正**：新增 Strategy 5 — 偵測文件中的國家法規關鍵字：
- `qmsr`、`21 cfr 820`、`eu mdr`、`tfda`、`衛福部`、`pmda`、`anvisa`、`tga` 等
- 匹配後擴展至該法規 profile 的所有映射 ISO 13485 條款（`iso_mapped` 中 `status != NOT_APPLICABLE`）
- `unique_requirements.related_iso_clauses` 也納入擴展
- 支援動態爬取的法規 profile（透過 `name_en`/`name_zh`/`country_name` 欄位）

- `src/analysis/comparison_table.py`：`_match_doc_to_clauses()` 新增 Strategy 5（+87 行）；`to_flat_rows()` 非數字 segment 防護

### 14.1 下載前詢問下載者姓名

**背景**：舊版下載文件時不記錄是誰下載，不符合 21 CFR Part 11 對操作者識別的要求。

**修正方式**：

所有下載路徑（指令與按鈕）均加入姓名確認流程：

| 觸發方式 | 流程 |
|----------|------|
| 輸入「下載 QP-001」等指令 | 先確認檔案存在 → 詢問「請問您的姓名？」→ 收到姓名後執行下載 |
| 點擊文件卡片的「下載原始文件」按鈕 | 詢問「請問您的姓名？」→ 收到姓名後執行下載 |

- 姓名空白時提示重新輸入，不允許跳過
- 下載完成後寫入稽核紀錄，`action = "DOC_DOWNLOADED"`，`user_id` 為輸入的姓名
- `details` 包含 `filename`（去除時間戳前綴）及 `triggered_by`（`"command"` 或 `"action_button"`）

**修改位置**：
- `src/chainlit_app/app.py`
  - `on_download_original_file()` action callback（~第 6490 行）：改為詢問姓名後下載
  - `on_message()` 下載指令區（~第 9499 行）：先 dry-run 確認檔案，再詢問姓名
  - `on_message()` awaiting_download_name 攔截區（~第 8999 行）：處理姓名輸入，分別處理 action button 及指令兩種路徑

### 14.2 匯出報告加入下載統計欄位

**背景**：匯出的 Word/Excel 報告無法呈現每份文件被下載的狀況。

**新增**：`_build_download_stats(audit_records)` — 從稽核紀錄中統計每份文件的下載次數與最近 5 位下載者。

三種匯出報告均新增「下載次數」與「下載者（最近5筆）」兩欄：

| 報告 | 檔案 | 新增欄位位置 |
|------|------|-------------|
| 文件清單（現行版本） | `doclist_export.py` | 7 欄，最後 2 欄為下載統計 |
| 全部紀錄（含進版/作廢） | `doclist_export.py` | 10 欄，最後 2 欄為下載統計 |
| 文件更動紀錄（稽核） | `audit_export.py` | 8 欄，最後 2 欄為下載統計 |

**修改位置**：
- `src/utils/doclist_export.py`：新增 `_build_download_stats()`、更新 4 個 export 函式
- `src/utils/audit_export.py`：更新 `export_to_word()`、`export_to_excel()`
- `src/chainlit_app/app.py`：三個 handle export 函式注入 `download_stats`

## 十五、稽核驗證（verify）指令（2026-04-08）

> **commit**: `adb4a6c` feat(verify): add integrity verification command with hash chain check and data file fingerprints

### 15.1 設計背景

AI-QMS 的稽核紀錄使用 SHA-256 雜湊鏈確保不可竄改，但原本只在查看「文件更動紀錄」時附帶驗證訊息，缺乏獨立的驗證工具供稽核員使用。

更重要的問題是：`doc_hierarchy.json`、`document_store.json`、`document_registry.json` 等核心資料檔案沒有任何保護機制——直接修改這些檔案，系統無從得知。

### 15.2 verify 指令功能

輸入「**稽核驗證**」（或英文 `verify`）後，系統輸出完整驗證報告：

```
🔒 稽核紀錄完整性驗證報告

✅ Hash 鏈完整，紀錄未被竄改

📋 紀錄總數：142 筆
🕐 最早紀錄：2025-03-01 09:00:00
🕐 最新紀錄：2026-04-08 14:23:11

🔑 目前鏈尾 Hash（可對外留存比對）：
`a3f9c2d1e8b7...（完整 64 字元）`

📁 關鍵資料檔 SHA-256 指紋（可留存，日後比對是否被修改）
• `audit_log.json`：`9d4e1f2a3b...`
• `doc_hierarchy.json`：`c7a8b9d0e1...`
• `document_store.json`：`f2e3d4c5b6...`
• `document_registry.json`：`a1b2c3d4e5...`

💡 建議將本報告匯出或截圖留存，作為日後比對基準。
```

### 15.3 各項目說明

| 項目 | 說明 |
|------|------|
| **Hash 鏈驗證** | 逐筆重算 SHA-256，鏈斷裂時指出是第幾筆紀錄（record_id） |
| **鏈尾 Hash** | 整條稽核鏈的最終指紋，可截圖留存，日後重新執行 verify 比對 |
| **資料檔 SHA-256 指紋** | 對 4 個核心 JSON 檔案計算 SHA-256，任何檔案內容變動指紋即改變 |
| **使用方式** | 定期執行 → 截圖或匯出 → 日後比對，不一致代表資料在系統外被動過 |

### 15.4 語言支援

觸發關鍵字已加入所有 20 種語言的 locale 檔案：

- 繁中：`稽核驗證`、`驗證紀錄`、`完整性驗證`、`資料驗證`
- 簡中：`稽核验证`、`验证记录`、`完整性验证`
- 英文：`verify`、`integrity check`、`chain verify`
- 其餘 17 種語言各含本地化關鍵字及 `verify` 作為通用觸發詞

### 15.5 限制說明

此設計為**偵測工具**，非阻擋機制。由於 AI-QMS 為本地部署應用程式，執行者對自己機器擁有完整存取權，無法從技術層面阻止有意的竄改。verify 指令的價值在於：

1. 提供稽核員獨立的驗證工具
2. 讓比對基準可被截圖外部留存
3. 偵測無意的資料損壞
4. 對「懶惰竄改」（改了但未重算 hash）立即告警

**修改位置**：
- `src/chainlit_app/app.py`：新增 `handle_verify()` 函式（~第 4031 行）、`on_message` 加入 `cmd.verify` 處理
- `src/chainlit_app/locales/*.json`：全 20 個語言檔加入 `_commands.cmd.verify`，zh-TW 與 en-US 加入完整回應字串
- `docs/v3.6.0_Update_Notes.md`：本節
- `README.md`：中英文指令表新增 verify 說明
